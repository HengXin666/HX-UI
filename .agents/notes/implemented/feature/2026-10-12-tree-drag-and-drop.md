# Agent Note: 树的拖放

Status: implemented

## Problem

任务属于某个工作区。要把它移到另一个工作区, 当时只能进详情页改 `workspace` 字段
—— 那是一次"打开 -> 编辑 -> 保存"的三步操作, 而用户的心智动作只是"把这个拖过去"。
当树里同时有多个工作区、需要重新分配若干任务时, 这个代价会累积。

## Decision

封装 `DragDrop` (原生 HTML5 拖放), 把 (dragId, dropId) 交给调用方。

**用原生拖放而不是指针事件**: 原生的 `draggable` + `dataTransfer` 自带三件很难
自己写对的东西 —— 拖拽影像 (ghost image)、跨窗口投递、以及"松开即放置"的语义。
用指针事件重写等于把这三点都重做一遍。

**"能不能放"是回调而不是布尔**: "A 能不能拖到 B 上"通常不是 B 的静态属性, 而是
**两者的关系** (同一层才能排序, 不同类型的节点不能互放)。所以 `canDrop(dragId,
dropId)` 拿到双方 id 自己判, 而不是给每个节点挂一个 `droppable` 布尔。

**放下之后不自己改数据**: `onDrop` 只交出两个 id, 数据怎么变由调用方决定。

**用自定义 MIME** (`application/x-hx-node`): 避免接住从浏览器外拖来的文本或文件
—— 那些拖进来放下会触发一次语义完全不同的写入。

## Alternatives considered

**什么都不做, 靠详情页的 `workspace` 字段改** —— 这是零成本的选项, 且已经能用,
对单个任务的调整完全够。否决理由是它把"重新分配"这件事的成本固定在三次交互上,
而拖放的常见使用场景恰恰是**批量**重排 (一次拖五个)。单次成本不重要, 重复成本才重要。

**用指针事件 (pointerdown/move/up) 自己实现** —— 理由是它能支持触屏, 而原生
HTML5 拖放在触屏上不工作。否决理由是实现量: 拖拽影像要自己做 (一个跟随指针的
浮层)、自动滚动要自己做 (拖到列表边缘时滚)、放置判定要自己做 (命中测试)。
为触屏支持付出这三样, 不如**明确承认它不支持触屏**, 并在触屏上保留按钮入口。

**给每个节点挂 `droppable: boolean`, 由节点自己声明** —— 理由是调用方更简单,
不用写 `canDrop`。否决理由是它无法表达"关系"这类约束: "任务可以拖到工作区上,
但工作区不能拖到任务上"用布尔写不出来, 只能退化成在 `onDrop` 里静默忽略 ——
而静默忽略正是"拖了没反应, 不知道为什么不反应"的来源。

## Consequences

任务可以在工作区之间直接拖动重新分配, 且 `canDrop` 让非法投放**在悬停时就不显示
可放置反馈**, 而不是松手后无反应。代价有三: 触屏不支持 (必须有按钮兜底)、
`canDrop` 的判据由调用方维护 (判错会出现"能拖但放不下")、以及拖放会触发写入,
所以调用方需要自己做乐观更新与失败回滚。
