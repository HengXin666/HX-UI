# Agent Note: 可收起侧栏与顶栏导航

Status: implemented

Decision-ID: collapsible-rail

## Code

- `src/layout/CollapsibleRail.tsx`
- `src/index.ts`

## Problem

侧栏里同时装着两类东西: **导航** (几个项, 很少变) 和**内容** (任务树, 需要纵向空间)。
它们对空间的需求是相反的 —— 导航只要一条, 内容要尽可能高。把导航竖着排成一列,
等于让最不需要空间的东西占掉一整列。

同时, 只有图标的窄态栏在只有几个项时反而更好用, 但当时的侧栏没有收起能力:
`SidebarNav` 只提供"一个项"的按钮, 没有任何容器级的宽度策略。

## Decision

新增两个通用件, 各自只解决一件事:

**`CollapsibleRail`** —— 容器级的宽度策略。关键点是"窄态"要**延时**切换:
收起有过渡动画, 若在动画第一帧就换成窄态渲染, 标题节点会瞬间消失而容器还在慢慢收,
视觉上像被抠掉。等动画走完 (150ms) 再切, 文字是跟着容器一起被推出去的。
窄态**不渲染**标题而不是 `hidden`: 后者会留在可访问性树里, 屏幕阅读器会在一个
只有图标的栏里念出全部文字。

**`NavTabs`** —— 同一批导航项的横向摆法。与 `SidebarNav` 共享的只有
"一个项 = 图标 + 标签 + 选中态"这个形状; 摆法、尺寸策略、溢出处理都不同。
选中态用 `aria-current="page"` 而不是自定义 class: 选中是**语义**, 不只是颜色。

## Alternatives considered

**什么都不做, 继续用竖排侧栏** —— 这是最省事的选项, 而且短期内完全能用:
几个导航项竖排并不难看, 用户也能找到。否决它的理由是它把纵向空间**永久**占掉了:
内容树越长, 这个代价越明显, 而导航项的收益是恒定的。越晚改, 布局越难动。

**给 `SidebarNav` 加一个 `orientation` 开关, 而不是新增组件** —— 理由是能少一个
导出、调用方只需改一个 prop。否决理由是这个开关会渗进每一处: 纵向时用
`flex-col` + 全宽 + 左对齐, 横向时用 `flex-row` + 自适应宽 + 居中, 窄态收缩策略
也不同。一个组件里塞两套布局, 等于两套布局都只有一半的可读性, 而且它们会开始
互相牵制 (改横向的溢出处理会碰到纵向的)。

**`CollapsibleRail` 立刻切换窄态 (不延时)** —— 理由是代码更简单, 少一个 state 和
一个 effect。否决理由是它会在动画期间产生可见跳变: 标题先消失、容器再收窄,
两件事不同步。这个延时不是调参, 它是"渲染模式"与"视觉过渡"的时间对齐。

## Consequences

导航挪进顶栏后, 左列整列还给内容树, 且可以收起到只留图标。顶栏因此变挤 ——
这是这个取舍的直接代价: 顶栏要同时装下导航与状态读数, 窄视口下需要另行处理。
两个组件都不含业务词, 任何"导航 + 内容"的页面都能直接用。
