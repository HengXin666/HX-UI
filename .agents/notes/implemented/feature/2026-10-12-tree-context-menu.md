# Agent Note: 树的右键菜单

Status: implemented

Decision-ID: tree-context-menu

## Code

- `src/layout/ContextMenu.tsx`
- `src/index.ts`

## Problem

树的行很窄, 而一行上可能有四五个动作 (重命名 / 归档 / 删除 / 打开仓库 / 复制路径)。
把它们全摆成行尾按钮会把标签挤没; 只留一个"更多"按钮又需要一次点击才能看到动作,
且那个按钮本身也要占宽度。

## Decision

封装 `ContextMenu` (基于 radix 的 context-menu), 行级动作走右键。

**右键与行尾按钮并存**, 不是二选一: 行尾按钮解决"我知道有这个动作, 我要点它",
右键解决"我在这一行上, 我想对它做点什么"。前者是**发现**(看见才知道有),
后者是**意图**(先有意图再找入口)。所以最常用的动作 (重命名) 留按钮, 全部动作进右键。

**`disabled` 与 `destructive` 是能力声明, 不是样式开关**: `disabled` 表示
"这个动作此刻不适用"(未绑定的工作区不能归档), `destructive` 表示"做了不好撤销"。
调用方声明意图, 视觉由组件统一决定 —— 否则每个页面都会自己调一遍红色。

## Alternatives considered

**什么都不做, 把动作全塞进行尾的"更多"下拉** —— 这是最省事的选项, 而且已有一套
dropdown-menu 的封装可以直接复用。否决理由是它在树里**会打架**: 每一行都多一个
按钮, 而树的行本来就只有几十像素高、宽度还被路径吃掉; 再加一个常驻按钮, 标签
就没有位置了。右键是零宽度的入口。

**自己用 `popover` + 坐标定位实现右键菜单** —— 理由是能完全控制样式与行为, 且
不依赖 radix 的 context-menu。否决理由是三件必须自己写对的事: 视口边缘的翻转
(靠近右下角时菜单要往左上弹)、点击外部关闭与焦点陷阱、以及键盘导航。
radix 已经把这三件做完了, 重写一遍只会得到一个更差的版本。

**只在右键里放动作, 不留任何行尾按钮** —— 理由是界面最干净。否决理由是
**可发现性**: 新用户不会去右键一个看起来只是文字的行, 于是重命名这类高频动作
会变成"只有老手知道"的功能。行尾按钮是给第一次用的人的。

## Consequences

行上可以承载任意多个动作而不占宽度, 且动作的适用性 (disabled) 与危险性
(destructive) 有统一表达。代价是动作**不可发现** —— 不知道能右键的人看不到它们,
所以高频动作必须同时保留按钮入口, 这条约束会长期存在。
