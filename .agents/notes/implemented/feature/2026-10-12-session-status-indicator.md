# Agent Note: 列表项行首状态指示与树的行尾附加位

Status: implemented

Decision-ID: session-status-indicator

## Code

- `src/layout/SessionStatusDot.tsx`
- `src/index.ts`

## Problem

列表型界面需要回答一个反复出现的问题: "这一项现在怎么样"。本库已有的
`StateDot` 只有颜色一个维度 (五档语气), 表达不了"正在动"这件事 —— 它渲染的
永远是一个静止的点。于是每个使用方都在自己拼: 有人在行里塞一个第三方 spinner,
有人写一个 `animate-pulse` 的 span, 有人干脆只在文字里加"(进行中)"。

三处判据分叉的后果是可见的: 转圈的直径、圆点的直径、行首占位宽度各不相同, 同一
列表里"在跑的行"与"停下的行"文字起点差几个像素; 颜色也不统一, 有人用主色, 有人
用绿色, 有人用蓝色。这些差异单看一行都不刺眼, 一列扫下来就很吵。

同时 `TreeNav` 的 `TreeNode` 只能表达"图标 + 标签 + 一段文本附加信息 + 角标"。
行首没有状态位; 行尾的附加内容必须是纯文本 (由本行统一字号与颜色), 想放一个相对
时间组件或一个操作按钮就只能改组件本身。

## Decision

### 一、新增 `SessionStatusDot` (`src/layout/SessionStatusDot.tsx`)

```ts
export type SessionStatus = "running" | "unread" | "idle" | "pending-input";
```

四态不是四件互不相干的事, 而是同一条轴上的四个位置: 执行中 (转圈) → 等待外部
输入 (脉冲点) → 执行结束且结果未被查看 (实心点) → 无状态 (不渲染)。前三态互斥,
调用方只需回答"在跑 / 在等 / 有未读"三个布尔量, 尺寸、颜色、动画由组件统一决定。

| status | 视觉 | 语义 |
|---|---|---|
| `running` | 主色弧线 + `animate-spin` | 正在执行 |
| `unread` | `bg-emerald-500` 实心点 | 已完成, 结果未查看 |
| `pending-input` | `bg-amber-500` 脉冲点 | 等待输入 |
| `idle` | 返回 `null` | 无状态, 不渲染也不占位 |

三条关键取舍:

1. **`idle` 返回 `null` 而不是一个占位空盒。** 留空盒会让整列空盒看起来像加载
   失败, 也让调用方无法用一次判断把这一格整体省掉。这与 `IconSlot` 的空值语义一致。
2. **外框固定 `size-3.5` 并居中。** 弧线与圆点直径不同, 各自撑开宽度会让同一列的
   文字起点随状态漂移。固定外框后, 指示器占的横向空间与状态无关。
3. **转圈用 CSS `animate-spin` 而不是本库已有的 `motion`。** 一个 1px 描边圆加一条
   透明边就是弧线, 零额外产物; `motion` 在本库承担的是需要编排与中断的进出场动效,
   把单元素匀速旋转交给它只是把一行 CSS 换成一次 JS 订阅, 并让本组件在无 JS 环境
   下失去指示。

无障碍上, 视觉是点、无障碍树里是文字: `label` 可覆盖, 省略时每一态都有兜底文案。
把兜底做成必需项而不是可选, 是因为"不传就不渲染"在视觉上看不出任何区别, 于是
绝大多数调用点会省掉它。

### 二、`TreeNode` 增加 `status` 与 `trailing` (`src/layout/tree-parts.tsx`)

行渲染顺序固定为: **状态点 → 展开箭头 → 图标 → 标签 → `meta` → `trailing` → 角标**。

- `status` 复用上面的四态, 省略与 `"idle"` 等价。
- `trailing` 排在 `meta` 之后、`badge` 之前, 与 `meta` 的分工是: `meta` 是"同一类
  事实的纯文本" (大小、数量), 由本行统一字号与颜色; `trailing` 是调用方自备的节点
  (相对时间、操作按钮、组合片段), 本行不替它决定长什么样。两者并存, 是为了让
  "右端还有东西"既可以用最省事的文本, 也可以直接放组件, 而不必为了塞一个按钮去
  放宽 `meta` 的类型 —— 一旦 `meta` 变成 `ReactNode`, 它就不再能保证视觉一致。

`TreeNav` 只把 `SessionStatus` 再导出, 键盘与展开逻辑一行未动: 状态指示是**行**的
属性, 与"哪些行可见"无关。

### 三、导出 (`src/index.ts`)

`SessionStatusDot`、`SessionStatus`、`SessionStatusDotProps` 从库入口导出; 使用方
不需要为它单独引路径。

## Alternatives considered

**什么都不做 (各使用方自己拼转圈与圆点)**: 最强的理由是零改动, 而且每个使用方对
"什么算完成"的定义确实不同 —— 有人按进程退出算, 有人按结果落盘算, 组件无法替它们
决定。否决理由: 这个分歧只在**状态从哪来**这一层, 不在**状态长什么样**这一层。把
前者留给调用方、把后者收敛成一处, 正是本库其余组件一直在做的事; 而现状是后者也
被复制了, 复制出来的尺寸与颜色已经不一致。

**复用 `StateDot`, 给它加一个 `spin` 属性**: 最强的理由是两者都是"一个小圆点表示
状态", 合并可以少一个组件, 调用方也不必在 `tone` 与 `status` 之间做选择。否决理由:
`StateDot` 的 `tone` 是**颜色轴** (ok / warn / error / idle / busy), 与这里的
**生命周期轴** (在跑 / 在等 / 有未读) 不正交 —— 一条"失败的未读"在颜色轴上要红色、
在生命周期轴上要实心点, 两个轴相乘会得到十几种组合, 而其中大多数组合没有意义。
更关键的是语义默认值: 这里的 `unread` 必须默认绿、`pending-input` 必须默认琥珀,
这在该轴上是定义的一部分, 在 `StateDot` 里只是调用方的一个参数。合并的结果是
调用点重新开始各写各的映射表。

**把状态位做成 `TreeNode` 的一个 `ReactNode` (即调用方自己传节点)**: 最强的理由是
最灵活, 不需要为新状态改组件。否决理由: 灵活性正是问题所在 —— 每个调用点都要自己
决定尺寸、颜色与动画, 于是又回到"同一列表里三种转圈"。类型上也无法表达"这一行
没有状态"与"这一行状态未知"的区别。

**只加 `status`, 不加 `trailing`**: 最强的理由是 `meta` 已经能放文本, 而"行尾还要
放组件"目前没有第二个使用方 (YAGNI)。否决理由: 这是同一行右端的一次改动, 分成两次
做意味着 `TreeRow` 的渲染顺序要改两遍、文档要写两遍; 而且 `meta` 与 `trailing` 的
分工必须在同一个决策里说清, 否则下一个人会把组件塞进 `meta` 并把它的类型放宽成
`ReactNode`, 那一步会让整行的视觉一致性失效。

## Consequences

**变好的**: 状态指示的尺寸、颜色与动画收敛到一处, "正在执行 / 待查看 / 等待输入"
在任何列表里长得一样; `idle` 不占位, 调用方可以整列无状态而不留空档; `TreeNode`
的行尾从此既能放文本也能放组件, 且两者的分工写在了类型注释里; 无障碍文本有兜底,
调用点忘记传 `label` 时读屏仍然得到一句人话。

**变差的**: `TreeNode` 多出两个可选字段, 行渲染的分支变多, `TreeRow` 的可读性略降;
`SessionStatus` 与 `StateTone` 是两个相似但不互通的类型, 使用方需要在两者之间做一次
选择 (上面的备选里说明了为什么不合并)。`trailing` 是任意节点, 组件无法保证调用方
塞进去的东西在窄容器里不撑破行 —— 这一条只能靠使用方自己加 `truncate`。
